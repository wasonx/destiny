# 甄算 1.0 完整版范围冻结说明

日期：2026-05-30

## 1. 范围结论

甄算 1.0 完整版采用“A+B 合并范围”：

- A：正式商业上线版。
- B：知识库专业版。

本版本的目标是把当前已经跑通的 MVP 推进到“可正式运营、可维护、可解释、可继续扩展”的版本。它不是只做演示，也不是一次性完成未来所有命理体系和商业能力。

本版本必须包含：

- 真实微信小程序登录。
- 手机号模拟验证码登录。
- 客户、后端编辑人员、平台管理人员三类账号。
- 原生微信小程序，不做 H5 转小程序。
- H5 / Web 与小程序共用同一套后端 API。
- 可视化知识库后台。
- Neo4j 图计算与图谱路径查询。
- 图谱可视化后台。
- 免费版 / 付费完整版报告分层。
- 商城、会员、积分、权益、订单、退款和发货的第一版闭环。

本版本明确暂不接入：

- 真实微信支付。
- 真实微信退款。
- 真实腾讯云短信。
- 真实快递查询。

这些外部接口只预留数据结构、状态机和 provider 边界，不在 1.0 里配置真实商户密钥、短信密钥、支付证书或快递接口密钥。

## 2. 产品边界

### 2.1 客户端范围

第一版正式客户端包含两套前端：

- 微信小程序：面向微信生态用户，必须使用原生小程序开发，保留 WXML、WXSS、JS 和微信原生 API。
- H5 / Web：面向浏览器访问和运营验证，继续使用现有 React / Vite 技术栈。

两套前端共用：

- 同一套甄算后端 API。
- 同一套客户账号、报告、订单、权益和知识库数据。
- 同一套报告生成和图计算结果。

两套前端不共用：

- 页面代码。
- 路由系统。
- 登录能力的端侧实现。
- 平台专属能力，例如小程序电子罗盘。

### 2.2 小程序必做能力

小程序 1.0 必须具备：

- 微信真实登录，使用 `wx.login` 获取 code，后端换取 openid / unionid。
- 手机号模拟验证码登录入口。
- 报告生成入口。
- 免费版报告查看。
- 付费完整版报告生成或升级入口。
- 报告历史。
- 商城商品列表。
- 商品详情。
- 订单创建。
- 人工支付状态展示。
- 会员与积分展示。
- 权益余额展示。
- 收货地址管理。
- 实物订单发货状态展示。
- 退款申请入口。
- 拟物版电子罗盘，用于房屋朝向采集。

### 2.3 H5 / Web 必做能力

H5 / Web 1.0 必须具备：

- 手机号模拟验证码登录。
- 客户报告生成与历史查看。
- 商城、会员、积分、订单的基础客户视图。
- 后台管理入口。
- 可视化知识库后台。
- 图谱可视化后台。

H5 不要求调用小程序专属能力，例如 `wx.login` 和设备电子罗盘。

## 3. 账号与权限边界

### 3.1 客户

客户用于购买商品、查看权益、生成报告、查看报告历史、维护收货地址和申请退款。

客户登录方式：

- 微信小程序真实登录。
- 手机号模拟验证码登录。
- 扫码登录。

客户权限边界：

- 只能访问自己的报告、订单、地址、权益、积分和会员信息。
- 不能访问后台知识库、规则、模板、订单管理和系统设置。

### 3.2 后端编辑人员

后端编辑人员用于维护知识内容，但不能管理平台关键配置。

可做：

- 新建和编辑知识条目草稿。
- 新建和编辑分析规则草稿。
- 新建和编辑报告模板草稿。
- 使用测试台验证规则命中和报告效果。
- 查看图谱和报告溯源。

默认不可做：

- 管理平台账号。
- 修改支付、短信、模型密钥等系统配置。
- 直接发布线上知识、规则和模板。
- 处理订单退款和人工支付确认。

### 3.3 平台管理人员

平台管理人员负责系统运营和最终发布。

可做：

- 管理后台账号和角色。
- 发布、停用知识条目、规则和模板。
- 查看发布版本和审计日志。
- 管理客户、订单、权益、会员、积分和商品。
- 人工确认支付。
- 处理退款申请。
- 填写实物订单发货信息。
- 查看运维健康和系统配置。

## 4. 后端与数据边界

### 4.1 Node API

Node / Express 继续作为主 API，负责：

- 客户登录。
- 后台登录。
- 权限鉴定。
- 报告生成。
- 规则命中。
- 知识库管理。
- 图计算查询封装。
- 商城业务整合。
- 会员、积分和权益。
- 订单、支付占位、退款和发货。
- 审计日志。

### 4.2 PostgreSQL

PostgreSQL 存储业务事实：

- 用户账号。
- 客户身份绑定。
- 后台角色权限。
- 知识条目。
- 分析规则。
- 报告模板。
- 发布版本。
- 报告历史。
- 订单。
- 支付单。
- 退款申请。
- 实物库存。
- 收货地址。
- 会员。
- 积分流水。
- 权益账户。
- 审计日志。

### 4.3 Neo4j

Neo4j 存储和查询关系事实：

- 八字基础本体概念。
- 天干、地支、五行、阴阳、十神、四柱等关系。
- 知识条目解释哪些概念。
- 规则使用哪些知识和概念。
- 模板关联哪些规则和风险边界。
- 报告命中了哪些规则、知识、概念路径和模板。

Neo4j 不直接替代 PostgreSQL，不存订单、支付、会员、积分等业务主数据。

### 4.4 大模型

大模型负责组织表达，不负责自行创造理论依据。

报告生成链路应为：

```text
用户输入
  -> 排盘和特征计算
  -> 规则命中
  -> Neo4j 查询解释路径
  -> 读取已发布知识和模板
  -> 组装大模型上下文
  -> 生成报告表达
  -> 安全审查
  -> 保存报告、命中规则、知识来源和图谱路径
```

## 5. 知识库专业版范围

### 5.1 知识条目

知识条目必须支持：

- 标题。
- 正文。
- 所属模块。
- 标签。
- 来源。
- 适用范围。
- 风险边界。
- 关联概念。
- 版本号。
- 状态：草稿、已发布、已停用。

### 5.2 分析规则

分析规则必须支持：

- 所属模块。
- 触发条件。
- 优先级。
- 权重。
- 命中解释。
- 建议内容。
- 关联知识条目。
- 关联图谱节点。
- 关联风险边界。
- 状态：草稿、已发布、已停用。

### 5.3 报告模板

报告模板必须支持：

- 模板名称。
- 报告类型。
- 免费版 / 完整版适用范围。
- 段落结构。
- 表达素材。
- 禁用表达。
- 免责声明。
- 关联规则。
- 关联风险边界。
- 状态：草稿、已发布、已停用。

### 5.4 发布工作流

知识、规则和模板都必须支持：

- 草稿编辑。
- 发布。
- 停用。
- 发布版本记录。
- 发布人记录。
- 发布时间记录。
- 变更摘要。
- 后台审计日志。

报告生成只能读取已发布内容。草稿内容不得影响线上报告。

## 6. 图计算与可视化范围

### 6.1 图计算必做

1. 概念路径查询：从某个概念查询上下游关系。
2. 知识路径查询：从知识条目查询解释的概念和相关来源。
3. 规则路径查询：从规则查询使用的知识、概念和风险边界。
4. 模板路径查询：从模板查询关联规则和风险边界。
5. 报告溯源查询：从报告查询命中规则、知识、概念路径和模板。

### 6.2 图谱可视化必做

后台必须提供四类视图：

- 概念节点图。
- 知识关系图。
- 规则路径图。
- 报告溯源图。

交互必须支持：

- 节点搜索。
- 节点类型过滤。
- 关系类型过滤。
- 点击节点查看详情。
- 展开一跳关系。
- 展开多跳关系。
- 从知识、规则、模板、报告页面跳转到对应图谱上下文。

## 7. 报告与商业范围

### 7.1 报告分层

报告分为：

- 免费版报告：用于体验，内容更短，主要展示摘要、部分建议和升级入口。
- 付费完整版报告：消耗报告次数、会员权益或订单权益，展示完整结构、规则解释、风险边界和更完整建议。

### 7.2 权益扣减

付费完整版报告生成前必须校验权益。

可用权益来源：

- 购买报告次数包。
- 会员套餐赠送额度。
- 平台后台补发权益。
- 特定商品订单发放权益。

权益扣减必须写入流水，并能在后台溯源。

### 7.3 商城

商城第一版支持：

- 报告次数包。
- 月会员。
- 年会员。
- 数字资料。
- 实物商品。

实物商品支持：

- SKU 库存。
- 收货地址。
- 人工发货。
- 快递公司和快递单号手工录入。
- 退款申请。

第一版不接真实快递接口。

### 7.4 支付

支付第一版只做人工确认。

必须保留：

- 订单。
- 支付单。
- 支付状态机。
- 支付 provider 占位。
- 人工确认支付入口。
- 支付日志。

不得做：

- 微信支付 API V3 下单。
- 微信支付回调验签。
- 微信商户证书配置。
- 真实退款 API。

### 7.5 短信

短信第一版只做模拟发送。

必须保留：

- 短信 provider 边界。
- 验证码有效期。
- 错误次数限制。
- 发送频控。
- 模板编号字段。
- 短信签名字段。
- 发送日志。

不得做：

- 腾讯云短信真实发送。
- 腾讯云密钥配置。
- 真实短信费用相关逻辑。

## 8. 第一版验收标准

1. 小程序可以通过真实 `wx.login` 换取后端客户 token。
2. 手机号验证码登录仍然是模拟发送，但具备真实接入所需的数据边界。
3. 后台可以创建、编辑、发布、停用知识条目、规则和模板。
4. 报告生成只读取已发布知识、规则和模板。
5. Neo4j 可以查询概念、知识、规则、模板和报告路径。
6. 后台可以可视化查看概念图、知识关系图、规则路径图和报告溯源图。
7. 报告生成记录命中规则、知识来源、图谱路径、安全审查和权益扣减。
8. 免费版和付费完整版报告可以区分生成。
9. 付费完整版报告会校验并扣减权益。
10. 商城支持虚拟商品和实物商品。
11. 实物商品支持库存、收货地址、人工发货和退款申请。
12. 微信支付保持人工确认，不出现真实支付接口调用。
13. 腾讯云短信保持模拟发送，不出现真实短信接口调用。
14. 后台角色权限生效，客户不能访问后台管理接口。
15. 敏感后台操作写入审计日志。
16. 原生小程序、H5、后端 API、PostgreSQL、Neo4j 在服务器上部署并通过健康检查。

## 9. 实施优先级

### P0：正式用户入口

- 真实微信登录。
- 手机号模拟登录边界整理。
- 客户身份合并。
- 后台账号角色权限补强。

### P1：知识库可发布

- 知识条目专业字段。
- 分析规则专业字段。
- 报告模板专业字段。
- 草稿、发布、停用、版本、审计闭环。

### P2：图计算与报告溯源

- Neo4j 查询服务层。
- 知识、规则、模板、报告路径关系。
- 报告生成写入溯源。

### P3：图谱可视化

- 图谱统一 API。
- 后台节点图组件。
- 搜索、过滤、展开、详情面板。

### P4：报告分层和权益闭环

- 免费版报告。
- 付费完整版报告。
- 权益校验和扣减策略。
- 报告升级入口。

### P5：商业运营补强

- 商品管理。
- 订单管理。
- 人工支付确认。
- 退款处理。
- 实物库存和人工发货。
- 会员、积分和权益后台调整。

## 10. 范围冻结原则

后续开发按以下原则判断是否纳入 1.0：

- 能支撑真实运营的核心闭环，纳入。
- 能提高知识库可维护性和报告可解释性，纳入。
- 只是外部平台真实接口接入，且已有占位流程，暂不纳入。
- 会大幅拉长周期但不影响 1.0 上线验证，暂不纳入。
- 会导致前端从原生小程序转为跨端方案，不纳入。
- 会让大模型脱离本地知识库和图谱自行下结论，不纳入。

本文件作为 1.0 开发范围冻结依据。若后续新增需求，必须先判断属于 1.0、1.1 还是 2.0，再进入实施计划。
