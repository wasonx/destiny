# 甄算 1.0 完整版差距审计

日期：2026-05-30

依据：[甄算 1.0 完整版范围说明书](2026-05-30-zhensuan-1.0-full-scope-design.md)

## 审计结论

当前系统已经具备 1.0 的基础骨架：原生小程序、H5、后台、Node API、PostgreSQL、Neo4j 基础种子、人工支付闭环、会员积分权益和商城页面已经存在。

但 1.0 目标仍未完成。主要缺口集中在：

- 客户身份治理：微信真实登录、手机号模拟登录和扫码登录已经具备基础链路；已登录客户可绑定新的微信身份或手机号身份；后台可以查看、主动绑定、解绑客户身份并写入审计日志，后台已有审计日志查询页；后台已支持把冲突客户合并到目标客户并迁移报告、订单、会员、权益、积分、地址、退款等业务记录。
- 知识库发布工作流：已有知识、规则、模板基础接口和页面，但发布、停用、版本审计和“草稿不影响线上”尚未完整闭环。
- 图计算：已有 Neo4j 健康检查、概念列表和基础路径接口，但还没有知识、规则、模板、报告级路径查询和报告生成溯源。
- 图谱可视化：已有“八字本体图谱”静态页面，但还不是节点图、关系过滤、展开和详情面板式的可交互图谱。
- 报告分层：已有报告生成和权益扣减，但还没有免费版 / 付费完整版产品分层。
- 报告溯源：报告历史保存了上下文，但没有形成用户和后台可读的规则命中、知识来源、图谱路径溯源视图。

## 需求逐项状态

| 范围项 | 当前状态 | 证据 | 差距 |
| --- | --- | --- | --- |
| 真实微信登录 | 基本具备 | `miniprogram/utils/auth.js` 使用 `wx.login`；`server/auth/wechat-session-provider.mjs` 调用 code2Session；`customer_identities` 保存 openid / unionid；已登录客户可绑定新微信身份；后台可主动绑定、解绑身份并审计；后台可查询审计日志；后台可人工合并冲突客户 | 继续打磨小程序登录失败兜底和重新登录体验 |
| 手机号模拟登录 | 基本具备 | `/customer/otp/send`、`/customer/otp/verify`，`sms_otp_challenges`，mock code；已具备发送冷却、错误次数上限、`sms_delivery_logs` 发送日志和后台短信日志查询页 | 后续可补更细的运营告警与异常统计 |
| 真实腾讯云短信不做 | 符合范围 | 当前短信 provider payload 为 mock；后台系统设置和短信日志均明确显示模拟发送，未接真实腾讯云短信接口 | 后续接真实短信时只替换 provider，不改登录主流程 |
| 微信支付不做真实接口 | 符合范围 | `wechat-placeholder-provider.mjs`，后台人工 `mark-paid` | 后续需保持占位，不引入真实商户密钥 |
| 商城人工支付闭环 | 基本具备 | `payment_intents`、`markPaymentPaid`、权益发放、库存扣减 | 需要补后台异常处理、退款和发货操作体验 |
| 知识条目专业化 | 部分具备 | `knowledge_entries`、`KnowledgePage` | 字段、来源、标签、适用范围、风险边界、状态和版本能力需要补齐 |
| 规则专业化 | 部分具备 | `analysis_rules`、规则接口、规则引擎 | 需要关联图谱节点、关联知识、发布状态和命中解释可视化 |
| 模板专业化 | 部分具备 | `report_templates`、模板接口和页面 | 需要模板段落结构、禁用表达、免责声明、版本和发布闭环 |
| 发布工作流 | 缺失为主 | 现有状态字段有限 | 需要草稿、发布、停用、版本记录、发布审计、回滚依据 |
| Neo4j 概念图谱 | 部分具备 | `server/graph/bazi-seed-data.mjs`、`seed-bazi-ontology.mjs`、`graph-routes.mjs` | 当前路径接口多为内存种子数据，需落到 Neo4j 查询和更丰富关系 |
| 图计算查询 | 缺失为主 | 只有概念和概念路径接口 | 需要知识、规则、模板、报告维度的路径查询 |
| 图谱可视化 | 缺失为主 | `OntologyPage.tsx` 是静态卡片式展示 | 需要真正节点边图、搜索、过滤、展开、详情面板和页面跳转 |
| 报告溯源 | 部分具备 | `report_runs.structured_context` 保存上下文 | 需要结构化保存命中规则、知识、图谱路径，并提供后台溯源视图 |
| 免费/付费报告分层 | 缺失为主 | 当前报告生成只区分是否有客户 token 和报告额度 | 需要 report tier、免费摘要、完整版权益校验和前端展示 |
| 权益扣减 | 基本具备 | 登录客户生成报告会扣减 quota，不足返回 402 | 需要结合免费/付费报告分层重新梳理扣减策略 |
| 会员与积分 | 基本具备 | 会员、积分、权益账户和后台页面已存在；后台可批量处理已到期会员并写入审计日志 | 需要补更细的运营规则和溯源展示 |
| 合规和安全 | 部分具备 | 安全审查、免责声明、后台鉴权、审计日志查询存在 | 需要补用户协议、隐私政策和报告分层合规文案 |

## 阶段优先级建议

### 第一优先级：客户身份治理

真实微信登录已经具备基础链路。下一步要把三种登录入口沉淀成可运营、可审计的客户身份体系：

- 后台查看客户的微信、手机号和扫码登录身份。
- 客户主动绑定身份，后台可主动绑定身份并解绑异常身份。
- 手机号、openid、unionid 冲突时的人工合并流程已具备基础能力，合并会禁用源客户并迁移主要业务记录。
- 身份绑定、解绑、合并写入审计日志；其中后台主动绑定、解绑、合并和审计查询已具备基础能力。
- 小程序登录失败兜底和重新登录体验继续打磨。

### 第二优先级：发布工作流

知识库专业版必须避免草稿内容污染线上报告。必须补：

- 知识、规则、模板的状态机。
- 发布版本表。
- 发布操作审计。
- 已发布内容读取策略。
- 后台发布、停用和版本详情页面。

### 第三优先级：图计算与报告溯源

图计算是 1.0 的专业壁垒。必须补：

- Neo4j 查询服务层。
- 概念、知识、规则、模板、报告之间的关系写入和查询。
- 报告生成时记录命中路径。
- 报告历史页展示溯源摘要。

### 第四优先级：图谱可视化

可视化是后台可维护性的核心。必须补：

- 图谱 API 返回统一节点/边结构。
- 后台图谱页面使用可交互节点图。
- 搜索、过滤、展开、详情面板。
- 从知识、规则、模板、报告跳转到图谱上下文。

### 第五优先级：报告分层和商业补强

在登录、发布和溯源之后，再做产品层收费体验：

- 免费版报告。
- 付费完整版报告。
- 小程序/H5 报告升级入口。
- 权益扣减策略。
- 订单、会员、积分和退款后台体验补强。

## 不纳入 1.0 的边界

本审计确认以下项目仍不纳入 1.0：

- 真实微信支付 API。
- 真实微信退款 API。
- 真实腾讯云短信 API。
- 真实快递查询 API。
- 分销代理体系。
- 专家入驻和人工咨询平台。
- 多商户商城。
- 一次性写满 518400 种命盘解释。
- 一次性完整上线六爻和奇门全部体系。
- 实时联网搜索生成报告。

## 工作区注意事项

当前工作区存在 `miniprogram/project.config.json` 的未提交变化：微信开发者工具将 `libVersion` 从 `latest` 改为 `3.15.2`。该变更与 1.0 差距审计无关，暂不纳入本次提交。
