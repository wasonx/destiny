# 甄算可视化知识库后台设计

日期：2026-05-30

## 1. 背景与目标

甄算当前已经有 Web/H5、微信小程序 MVP、线上 Node/Express API、HTTPS 域名和 PostgreSQL 基础数据库。下一阶段要建设的是一套内部可维护的可视化知识库后台，用来承载传统术数知识、半自动规则引擎、报告模板、用户体系、会员权益、轻商城和后续商业运营能力。

第一版后台定位为内部专业工具，主要给你和核心团队使用。目标不是做一个花哨的 CMS，而是建立一套可解释、可发布、可回滚、可持续扩展的知识生产系统。

第一版必须做到：

- 管理知识条目、分析规则、报告模板。
- 支持八字本体图谱作为样板体系。
- 支持表单编辑与图谱路径查看。
- 支持本地知识库 + 在线大模型 API 生成报告。
- 支持客户、后端编辑人员、平台管理人员三类账号。
- 支持客户多方式登录、报告历史、会员、积分、轻商城。
- 轻商城支持虚拟商品和实物商品，实物商品第一版只做库存、收货地址、人工发货和退款状态。
- 微信支付先完成功能设计和数据结构预留，暂不接真实接口。

第一版不做：

- 实时联网搜索生成报告。
- 完整专家系统。
- 真实快递接口、复杂地区运费模板、自动退款接口。

## 2. 总体架构

```text
微信小程序 / H5
  -> 甄算 API
    -> 用户系统
    -> 报告生成服务
    -> 权益与积分服务
    -> MedusaJS 商城底座
    -> PostgreSQL
    -> Neo4j
    -> 在线大模型 API
```

系统边界：

- H5 使用 React/Vite 开发；微信小程序坚持原生微信小程序开发，使用 WXML、WXSS、JS 和微信原生 API，不采用 H5 代码转换为小程序的路线。
- H5 和微信小程序共用甄算 API、JSON 数据结构和可复用的纯 JS 工具函数，但页面、路由、登录能力和端侧交互分别按各自平台实现。
- PostgreSQL 负责业务数据、用户、权限、订单、权益、积分、草稿、发布状态、版本、报告历史。
- Neo4j 负责八字本体图谱、概念关系、知识依赖、规则路径、报告模板关联。
- MedusaJS 负责轻商城底座，包括商品、价格、购物车、订单、库存、支付状态和商城后台基础能力。
- 甄算 API 负责客户登录、后台鉴权、规则引擎、权益发放、报告生成、安全审查、短信验证码模拟/腾讯云短信适配、实物订单履约状态和业务整合。
- 在线大模型 API 只负责理解、组织和表达，不直接决定理论依据。

## 3. 用户系统

第一版包含三类账号。

### 客户

客户支持三种登录方式：微信登录、手机号验证码登录、扫码登录。三种方式最终归并到同一客户账号，优先使用 unionid、手机号或已绑定身份做账号合并，避免同一客户产生多个身份。

登录方式：

- 微信登录：小程序内使用微信 code 登录，后端换取 openid / unionid。
- 手机号验证码登录：H5 和小程序均可使用，后端发送短信验证码，校验通过后创建或登录客户账号。
- 扫码登录：PC/H5 展示登录二维码，客户用小程序或微信扫码确认后完成登录。

安全约束：

- 短信验证码必须有发送频率限制、错误次数限制、有效期和发送日志。
- 扫码登录二维码必须短时有效、一次性使用，并具备待确认、已确认、已过期、已取消状态。
- 账号绑定、解绑和身份合并必须写入审计日志，避免报告历史、会员权益和积分归属错乱。

短信策略：

- 短信服务商确认使用腾讯云短信。
- 第一版先使用模拟发送，不接真实腾讯云接口。
- 先设计短信签名、模板、场景、验证码有效期和发送日志结构。
- 第一版模板包含登录验证码和绑定手机号验证码。

能力：

- 创建或登录客户账号。
- 绑定微信身份、手机号或扫码会话。
- 查看自己的报告历史。
- 管理基础资料。
- 查看会员状态、积分余额、报告次数余额。
- 购买会员、次数包、数字资料。
- 使用权益生成报告。

### 后端编辑人员

后端编辑人员使用后台账号密码登录。

能力：

- 查看知识库后台。
- 创建和编辑知识条目草稿。
- 创建和编辑分析规则草稿。
- 创建和编辑报告模板草稿。
- 使用 AI 辅助抽取内容。
- 在测试台运行模拟报告。
- 默认不能管理平台账号、支付配置和核心系统参数。
- 默认不能直接发布线上内容，除非平台管理人员授权。

### 平台管理人员

平台管理人员使用后台账号密码登录。

能力：

- 管理后台账号、角色和权限。
- 发布、停用知识条目、规则和模板。
- 管理用户、订单、权益、积分。
- 管理会员套餐、商城商品、数字内容。
- 管理模型 API、系统配置、风险边界。
- 查看日志、报告记录、模型调用情况。
- 处理订单异常、权益补发、退款预留流程。

## 4. 知识库后台

后台主菜单第一版设计为：

```text
1. 总览
2. 用户管理
3. 会员与积分
4. 商城管理
5. 订单与支付
6. 八字本体图谱
7. 知识条目
8. 分析规则
9. 报告模板
10. 导入与 AI 抽取
11. 测试台
12. 发布版本
13. 系统设置
```

### 总览

展示：

- 知识条目数量。
- 规则数量。
- 模板数量。
- 待处理草稿。
- 已发布版本。
- 今日报告生成量。
- 今日模型调用量。
- 商城订单和权益发放概况。

### 知识条目

知识条目是理论解释的最小维护单元。

核心字段：

- 标题。
- 所属模块。
- 内容正文。
- 来源。
- 标签。
- 关联概念。
- 适用范围。
- 风险提示。
- 状态：草稿、已发布、已停用。
- 版本号。

### 分析规则

规则层采用半自动规则引擎。

规则字段：

- 适用模块。
- 触发条件。
- 优先级。
- 权重。
- 命中解释。
- 建议内容。
- 风险边界。
- 关联知识条目。
- 关联本体节点。
- 关联报告模板。
- 状态：草稿、已发布、已停用。

规则编辑方式：

- 表单式编辑为主。
- 自然语言辅助生成为辅。
- AI 生成的规则只能进入草稿，必须人工确认后发布。

### 报告模板

模板控制最终给用户看的结构、语气和安全边界。

模板字段：

- 模板名称。
- 所属模块。
- 适用报告类型。
- 段落结构。
- 可用表达素材。
- 禁用表达。
- 免责声明。
- 关联规则。
- 状态：草稿、已发布、已停用。

## 5. Neo4j 八字本体图谱

图数据库选择 Neo4j Community Edition。Neo4j 承载本体图谱与解释路径，不直接承载后台业务数据。

第一版以照见 / 八字作为样板体系，不立即覆盖完整 518400 种命盘解释，而是先建立可扩展骨架。

### 节点类型

```text
Concept        概念
Knowledge      知识条目
Rule           分析规则
Template       报告模板
RiskBoundary   风险边界
Source         理论来源
Module         产品模块
```

八字概念第一版覆盖：

- 天干：甲乙丙丁戊己庚辛壬癸。
- 地支：子丑寅卯辰巳午未申酉戌亥。
- 五行：木火土金水。
- 阴阳：阴、阳。
- 十神：比肩、劫财、食神、伤官、偏财、正财、七杀、正官、偏印、正印。
- 四柱：年柱、月柱、日柱、时柱。
- 藏干：地支内藏天干。
- 基础组合关系：合、冲、刑、害、破。

### 关系类型

```text
(:Concept)-[:BELONGS_TO]->(:Concept)       属于
(:Concept)-[:GENERATES]->(:Concept)        相生
(:Concept)-[:RESTRAINS]->(:Concept)        相克
(:Concept)-[:COMBINES_WITH]->(:Concept)    合
(:Concept)-[:CONFLICTS_WITH]->(:Concept)   冲
(:Concept)-[:PUNISHES]->(:Concept)         刑
(:Concept)-[:HARMS]->(:Concept)            害
(:Concept)-[:CONTAINS]->(:Concept)         藏干
(:Knowledge)-[:EXPLAINS]->(:Concept)       知识解释概念
(:Rule)-[:USES]->(:Knowledge)              规则引用知识
(:Rule)-[:TRIGGERS]->(:Template)           规则触发模板
(:RiskBoundary)-[:CONSTRAINS]->(:Rule)     风险边界约束规则
(:Template)-[:USES]->(:RiskBoundary)       模板使用风险边界
(:Knowledge)-[:FROM_SOURCE]->(:Source)     知识来自来源
```

第一版要能回答：

- 某个报告结论用了哪些知识。
- 某条规则来自哪些理论概念。
- 某个五行、十神、天干、地支影响哪些规则。
- 某个风险边界约束了哪些报告表达。
- 某条规则如何从本体关系路径命中。

## 6. 八字计算与测试台

八字计算采用成熟排盘算法或库，不自己从零手写历法、节气、时区和四柱换算。

第一版有两条入口：

```text
线上用户入口：
出生信息 -> 后端排四柱 -> 图谱/规则引擎 -> 大模型报告

后台测试入口：
手动输入四柱 -> 图谱/规则引擎 -> 查看命中路径和报告
```

测试台需要展示：

- 输入信息。
- 四柱结果。
- 五行分布。
- 十神结构。
- 命中的知识条目。
- 命中的规则。
- 走过的 Neo4j 路径。
- 使用的报告模板。
- 最终生成报告。
- 风险边界命中情况。

## 7. 报告生成链路

第一版不做实时联网搜索。报告由本地知识库、Neo4j 关系路径、规则引擎和在线大模型 API 共同完成。

```text
用户输入
  -> 输入校验
  -> 排盘/特征计算
  -> Neo4j 查询本体关系路径
  -> PostgreSQL 读取已发布知识、规则、模板
  -> 半自动规则引擎命中结构化结论
  -> 拼装大模型上下文
  -> 在线大模型生成报告
  -> 安全审查
  -> 保存报告历史
  -> 返回用户
```

大模型职责：

- 理解用户问题。
- 组织结构。
- 改写为克制、易读、亲民的表达。

大模型不负责：

- 自行决定理论依据。
- 自行创造规则。
- 直接给出绝对化结论。
- 给医疗、投资、法律等高风险建议。

## 8. 商城系统

商城底座选择 MedusaJS。MedusaJS 负责商品、价格、购物车、订单、库存、支付状态、客户、后台管理等基础电商能力。甄算自己负责客户登录、微信支付适配、权益发放、报告次数、会员、积分、收货地址、人工发货、退款状态、知识库和报告生成。

参考资料：

- Medusa Commerce Modules：https://medusajs.com/modules/
- Medusa Documentation：https://docs.medusajs.com/

第一版商品类型：

- 报告次数包。
- 月度会员。
- 年度会员。
- 数字资料。
- 实物商品。
- 后续预留专项咨询/预约。

实物商品第一版默认规则：

- 按 SKU 管库存。
- 未支付订单不锁库存。
- 人工标记支付成功后扣减库存。
- 支持客户收货地址：收货人、手机号、省市区、详细地址、默认地址。
- 第一版不接快递接口，由后台人工填写快递公司和快递单号。
- 运费采用固定运费 / 满额包邮，不做复杂地区运费模板。

第一版不做：

- 真实快递接口。
- 自动物流轨迹查询。
- 复杂仓储库存。
- 复杂促销。

商品分为三类：

### 权益型商品

购买后自动发放：

- 报告次数。
- 会员有效期。
- 模块访问权限。
- 专属模板/报告权益。

### 内容型商品

购买后自动解锁：

- PDF。
- 音频。
- 课程资料。
- 专题数字内容。

### 实物型商品

购买后进入人工履约流程：

- 扣减 SKU 库存。
- 使用客户收货地址。
- 后台人工发货。
- 后台填写快递公司和快递单号。
- 客户查看发货状态和物流单号。

### 退款规则

虚拟商品和实物商品都支持退款，但第一版采用人工审核：

- 虚拟商品未使用可全额退款。
- 已消耗的报告次数、已生效会员、已查看或已下载数字内容，进入人工审核退款。
- 实物商品未发货可退款。
- 实物商品已发货后进入人工售后处理。
- 第一版不接真实支付退款接口，只记录退款申请、审核状态和人工处理结果。

## 9. 微信支付预留设计

第一版先设计微信支付流程和数据结构，暂不接真实微信支付接口。

预留流程：

```text
客户选择商品
  -> 创建商城订单
  -> 创建支付单
  -> 返回预支付参数
  -> 客户完成微信支付
  -> 微信支付回调
  -> 校验签名和金额
  -> 更新订单为已支付
  -> 发放权益或解锁数字内容
  -> 写入权益流水
```

当前阶段实现范围：

- 订单模型。
- 支付单模型。
- 支付状态机。
- 退款申请和退款状态模型。
- 支付回调处理接口占位。
- 权益发放服务。
- 实物库存扣减服务。
- 人工发货和物流单号记录。
- 支付日志表。
- 人工标记支付成功的测试入口。

暂不实现：

- 微信商户号配置。
- 微信支付 API V3 签名。
- 真实预支付下单。
- 真实支付回调验签。
- 真实退款接口。

订单状态第一版：

```text
待支付
已支付
待发货
已发货
已完成
退款中
已退款
已关闭
```

虚拟商品支付成功后直接发放权益或解锁内容；实物商品支付成功后进入待发货。

## 10. 积分与会员体系

会员体系采用两个维度：付费会员和成长等级。

### 付费会员

付费会员解决“用户买了什么权益”。

```text
普通用户
月度会员
年度会员
```

普通用户：

- 基础体验额度。
- 查看报告历史。
- 可购买次数包、数字资料。

月度会员：

- 每月固定报告额度。
- 数字内容折扣。
- 部分会员专属内容。

年度会员：

- 更高月度额度。
- 更高折扣。
- 年度报告或深度报告权益。
- 优先体验新模块。

### 成长等级

成长等级解决“用户长期活跃和贡献”。

命名采用东方文化型：

```text
L0 启蒙
L1 入门
L2 明理
L3 通达
L4 参玄
```

等级来源：

- 使用频次。
- 报告生成次数。
- 积分累计。
- 消费累计。
- 活动参与。
- 邀请行为。

### 积分

积分用于运营激励，不在第一版直接等价现金。

获得积分：

- 登录。
- 完善资料。
- 生成报告。
- 购买商品。
- 购买会员。
- 邀请用户。
- 活动赠送。

使用积分：

- 兑换报告次数。
- 兑换数字资料。
- 兑换优惠券。
- 参与活动。

权益账户统一记录：

- 报告次数余额。
- 会员有效期。
- 积分余额。
- 数字内容解锁记录。
- 权益流水。
- 订单来源。
- 发放原因。
- 过期时间。

## 11. 状态与发布机制

知识、规则、模板采用三态：

```text
草稿
已发布
已停用
```

规则：

- 草稿不影响线上报告。
- 已发布才可被线上报告生成调用。
- 已停用保留历史，但不再参与命中。
- AI 抽取内容默认进入草稿。
- 平台管理人员负责发布和停用。

发布版本需要记录：

- 版本号。
- 发布人。
- 发布时间。
- 发布内容范围。
- 变更摘要。
- 回滚目标版本。

## 14. 风险与约束

- 当前服务器为轻量配置，PostgreSQL + Neo4j + Node + MedusaJS 可先小规模运行，但需要控制内存和进程数量。
- Neo4j 不暴露公网，只允许本机或内网访问。
- 数据库、支付、模型 API 密钥必须放在服务器受限配置文件中。
- 微信支付未正式接入前，所有支付相关功能只能走模拟或人工确认。
- 腾讯云短信未正式接入前，验证码只走模拟发送；先保留短信签名、模板、场景和日志结构。
- 实物商品第一版不接快递接口，物流信息由后台人工填写。
- 退款第一版不接真实退款接口，走退款申请、人工审核、人工处理结果记录。
- 积分第一版不直接抵现金，降低财务和合规复杂度。
- 报告生成必须保留免责声明和安全审查。

## 15. 当前决策摘要

- 架构：PostgreSQL + Neo4j + MedusaJS + Node/Express + React Admin。
- 图数据库：Neo4j。
- 商城底座：MedusaJS。
- 支付：微信支付先设计，不接真实接口。
- 商品：报告次数包、会员套餐、数字资料、实物商品。
- 用户：客户、后端编辑人员、平台管理人员。
- 客户登录：微信登录 + 手机号验证码登录 + 扫码登录。
- 短信：腾讯云短信，第一版先做签名和模板设计，接口用模拟数据。
- 实物履约：SKU 库存、收货地址、人工发货、人工填写物流单号。
- 退款：虚拟和实物都支持退款申请，第一版人工审核和人工处理。
- 小程序工具：原生小程序实现拟物电子罗盘，放在线上联调阶段。
- 会员体系：普通用户、月度会员、年度会员。
- 成长等级：启蒙、入门、明理、通达、参玄。
- 知识样板：照见 / 八字。
- 编辑体验：表单编辑 + 图谱查看。
- 发布机制：草稿、已发布、已停用。
