# 甄好算 1.0 正式运营范围冻结版

日期：2026-06-01

## 1. 冻结结论

甄好算 1.0 按 **A 商业运营版 + B 专业知识库版** 冻结范围。

本版本目标不是继续做 MVP，也不是一次性做成终局平台，而是把已经跑通的系统推进为可以真实运营、可以维护、可以解释、可以部署和可以上传微信小程序的正式版本。

本范围已确认：

- A 商业运营版要做。
- B 专业知识库版要做。
- A 中的真实微信支付先不做。
- A 中的真实腾讯云短信先不做。
- 手机号登录使用模拟验证码。
- 微信小程序登录必须接真实微信登录。
- 图计算必须做。
- 图谱可视化必须做。
- 完成后必须把原生微信小程序上传到当前微信小程序账号。

## 2. 1.0 必做范围

### 2.1 客户端

1. 原生微信小程序。
2. H5 / Web。
3. 同一套后端 API。
4. 同一套客户、报告、订单、会员、积分、权益和知识库数据。

微信小程序必须保持原生开发，使用 WXML、WXSS、JS 和微信原生 API。不得采用 H5 转小程序，不得用 WebView 承载 H5 页面来替代原生小程序页面。

### 2.2 登录体系

微信小程序登录必须真实接入：

1. 小程序端使用 `wx.login` 获取 code。
2. 后端调用微信接口换取 openid / unionid。
3. 后端创建或复用客户账号。
4. 后端保存微信身份绑定记录。
5. 登录成功后返回客户 token。
6. 客户 token 继续复用现有报告、商城、会员、积分和权益接口。

手机号登录第一版使用模拟验证码：

1. 保留发送验证码接口。
2. 保留验证码校验接口。
3. 保留过期时间、错误次数、频控和发送日志。
4. 保留腾讯云短信签名、模板、场景和 provider 边界。
5. 后续接真实腾讯云短信时，只替换 provider，不重写主流程。

### 2.3 商业运营

A 商业运营版必须包含：

1. 商品管理。
2. 虚拟商品。
3. 实物商品。
4. SKU 库存。
5. 收货地址。
6. 订单创建。
7. 人工支付确认。
8. 退款申请。
9. 人工退款处理记录。
10. 人工发货。
11. 快递公司和快递单号手工录入。
12. 会员。
13. 积分。
14. 权益账户。
15. 权益发放、扣减、过期和补发。

支付第一版只做人工确认。人工确认支付成功后，系统继续触发虚拟权益发放、实物库存扣减、发货状态流转或数字内容解锁。

### 2.4 专业知识库

B 专业知识库版必须包含：

1. 知识条目。
2. 分析规则。
3. 报告模板。
4. 草稿、已发布、已停用状态。
5. 发布记录。
6. 版本记录。
7. 发布审计。
8. 后台编辑人员权限。
9. 平台管理人员权限。

知识条目需要支持标题、正文、模块、标签、来源、适用范围、风险边界和关联概念。

分析规则需要支持触发条件、优先级、权重、命中解释、建议内容、关联知识和关联图谱节点。

报告模板需要支持报告类型、段落结构、表达素材、禁用表达、免责声明、关联规则和状态。

线上报告只能读取已发布内容。草稿内容不得影响线上报告。

### 2.5 图计算

图计算必须真实接入 Neo4j，不能用静态页面或假数据替代。

Neo4j 在 1.0 中承担本体图谱和解释路径能力，必须支持：

1. 概念路径查询。
2. 知识路径查询。
3. 规则路径查询。
4. 模板路径查询。
5. 报告溯源路径查询。
6. 报告生成时记录命中规则、知识来源、图谱节点、图谱边和模板快照。

PostgreSQL 仍然是业务主库。Neo4j 不替代订单、支付、会员、积分、权益和客户等业务主数据。

### 2.6 图谱可视化

后台必须提供可操作的图谱可视化界面，至少包含：

1. 概念节点图。
2. 知识关系图。
3. 规则路径图。
4. 报告溯源图。

交互必须支持：

1. 搜索节点。
2. 按节点类型过滤。
3. 按关系类型过滤。
4. 点击节点查看详情。
5. 展开一跳关系。
6. 展开多跳关系。
7. 从知识、规则、模板、报告页面跳转到对应图谱上下文。

### 2.7 报告系统

报告必须支持免费版和付费完整版。

免费版用于体验，展示较短摘要、部分建议和升级入口。

付费完整版必须：

1. 校验报告次数、会员权益或订单权益。
2. 权益不足时拒绝生成。
3. 生成成功后扣减权益。
4. 保存权益流水。
5. 保存规则命中。
6. 保存知识来源。
7. 保存图谱路径。
8. 保存安全审查结果。
9. 展示免责声明和风险边界。

大模型可以用于组织表达，但结论依据必须来自本地知识库、规则引擎和 Neo4j 图谱。不得让大模型脱离本地知识库和图谱自行下结论。

### 2.8 小程序专属能力

原生微信小程序必须包含拟物版电子罗盘，用于记录房屋朝向。

电子罗盘必须使用微信小程序原生能力读取方向信息。H5 不要求实现同等设备能力。

### 2.9 合规和安全

1. 保留用户协议。
2. 保留隐私政策。
3. 保留报告免责声明。
4. 报告不得给出医疗、投资、法律等确定性高风险建议。
5. 客户只能访问自己的报告、订单、地址、会员、积分和权益。
6. 后台接口必须按角色鉴权。
7. 后台敏感操作必须写入审计日志。

## 3. 1.0 明确不做范围

以下内容不纳入甄好算 1.0：

1. 真实微信支付 API。
2. 真实微信退款 API。
3. 真实腾讯云短信 API。
4. 真实快递查询 API。
5. 分销代理体系。
6. 多商户商城。
7. 专家入驻。
8. 人工咨询平台。
9. 一次性写满 518400 种八字命盘解释。
10. 一次性完整上线六爻全部体系。
11. 一次性完整上线奇门全部体系。
12. 实时联网搜索生成报告。

这些能力可作为 1.1 或 2.0 继续规划。

## 4. 交付完成标准

甄好算 1.0 只有在以下条件全部满足时，才视为完成：

1. 本地服务端测试通过。
2. 本地前端构建通过。
3. 小程序静态验证通过。
4. 服务器部署通过。
5. H5 可以通过 HTTPS 访问。
6. 后台可以通过 HTTPS 访问。
7. API 健康检查通过。
8. PostgreSQL 迁移完成。
9. Neo4j 健康检查通过。
10. 后台可以验证图计算接口。
11. 后台可以验证图谱可视化。
12. 小程序可以使用真实微信登录链路。
13. 手机号验证码仍为模拟登录。
14. 微信支付仍为人工确认，不出现真实支付接口调用。
15. 腾讯云短信仍为模拟发送，不出现真实短信接口调用。
16. 免费版和付费完整版报告可以区分生成。
17. 付费完整版报告会校验并扣减权益。
18. 报告记录中能查看规则命中、知识来源和图谱路径。
19. 商城、订单、会员、积分、权益、退款和发货闭环可用。
20. 原生微信小程序通过上传前检查。
21. 原生微信小程序上传到当前微信小程序账号。

## 5. 后续版本边界

### 5.1 1.1 可考虑

1. 接入真实微信支付。
2. 接入真实微信退款。
3. 接入真实腾讯云短信。
4. 接入真实快递查询。
5. 丰富知识库内容。
6. 丰富图谱关系密度。
7. 优化报告表达和运营转化。
8. 增加更多运营活动和优惠策略。

### 5.2 2.0 可考虑

1. 多术数体系。
2. 更复杂的图谱推理。
3. 专家系统。
4. 人工咨询。
5. 分销代理。
6. 多商户。
7. 更完整的用户成长体系。

## 6. 冻结原则

后续开发、测试、部署和验收均以本文档为准。

如果新增需求符合以下条件，可以纳入 1.0：

1. 能直接支撑 A 商业运营版或 B 专业知识库版闭环。
2. 不引入真实微信支付、真实腾讯云短信、真实快递等外部生产接口。
3. 不改变原生微信小程序路线。
4. 不让大模型脱离本地知识库、规则和图谱自行生成结论。
5. 不显著扩大上线周期。

如果新增需求超出以上边界，应进入 1.1 或 2.0 规划，不打断 1.0 交付。
