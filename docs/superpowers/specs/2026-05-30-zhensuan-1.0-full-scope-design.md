# 甄算 1.0 完整版范围说明书

日期：2026-05-30

## 1. 定位

甄算 1.0 完整版不是继续做 MVP，也不是一次性做成长期大平台。它的目标是把当前已经跑通的系统推进为“可运营的正式版本”：用户可以真实微信登录，产品可以按免费/付费报告分层，后台可以维护知识、规则和模板，Neo4j 图计算可以参与解释链路，后台可以可视化查看图谱和报告溯源。

本版本采用“A+B 合并范围”：

- A：1.0 正式商业上线版。
- B：知识库专业版。

但 A 中的真实微信支付和真实腾讯云短信暂不接入。支付继续走人工确认，手机号继续走模拟验证码登录。微信登录必须接真实小程序登录能力。

## 2. 必做范围

### 2.1 真实微信登录

小程序端使用 `wx.login` 获取 code，后端调用微信接口换取 openid / unionid，并创建或绑定客户账号。

要求：

- 小程序启动或用户触发登录时调用真实微信 code 登录。
- 后端支持微信登录 provider，配置 appid、secret 和接口地址。
- 后端保存微信身份绑定记录，包括 openid、unionid、绑定客户、绑定时间和来源。
- 若 unionid 或已绑定 openid 已存在，应复用原客户账号。
- 登录成功后返回客户 token，继续复用现有客户会话模型。
- H5 手机号模拟登录和扫码登录保留，不替代小程序微信真实登录。

### 2.2 手机号模拟登录

手机号验证码仍然使用模拟发送，不接腾讯云短信真实接口。

要求：

- 保留手机号验证码登录接口。
- 验证码发送、校验、过期、错误次数和频控按真实短信接入标准设计。
- 发送日志、场景、模板编号、签名字段保留。
- 后续接腾讯云短信时只替换 provider，不重写登录流程。

### 2.3 微信支付暂不接真实接口

本阶段不接微信支付 API V3，不配置商户证书，不处理真实回调。

要求：

- 保留订单、支付单、退款申请和支付状态机。
- 支付成功仍由后台人工确认。
- 人工确认后继续触发权益发放、库存扣减、发货状态或数字内容解锁。
- 支付 provider 继续保留微信占位实现，并明确返回“尚未接入真实接口”。
- 数据结构要能支撑后续真实微信支付接入。

### 2.4 知识库专业化

知识库从 MVP 升级为内部专业生产系统。

要求：

- 知识条目支持标题、正文、模块、标签、来源、适用范围、风险边界、关联概念、版本和状态。
- 规则支持触发条件、优先级、权重、命中解释、建议内容、关联知识、关联图谱节点和状态。
- 报告模板支持报告类型、段落结构、表达素材、禁用表达、免责声明、关联规则和状态。
- 知识、规则、模板都支持草稿、已发布、已停用。
- 发布动作记录发布人、发布时间、变更摘要和版本号。

### 2.5 图计算

Neo4j 不只作为概念仓库，还要参与分析和溯源。

要求：

- 支持按概念查询上下游关系。
- 支持按知识条目查询关联概念。
- 支持按规则查询使用的知识、概念和风险边界。
- 支持按报告查询命中的规则、知识、概念路径和模板。
- 支持路径查询，用来展示“为什么得出这个结论”。
- 图计算结果进入报告生成上下文，但最终表达仍由报告服务和大模型组织。

### 2.6 图谱可视化

后台需要一套可操作的图谱可视化界面。

第一版视图：

- 概念节点图：查看天干、地支、五行、十神、四柱等概念关系。
- 知识关系图：查看知识条目解释了哪些概念。
- 规则路径图：查看规则引用了哪些知识和概念。
- 报告溯源图：查看一份报告命中了哪些规则、知识和图谱路径。

交互要求：

- 搜索节点。
- 按类型过滤节点和边。
- 点击节点查看详情。
- 展开一跳或多跳关系。
- 从知识、规则、模板、报告页面跳转到对应图谱视图。

### 2.7 报告分层

报告产品从单一生成升级为免费版和付费完整版。

要求：

- 免费版用于体验，内容更短，展示重点摘要和部分建议。
- 付费完整版消耗报告次数、会员权益或订单权益。
- 报告生成前检查权益。
- 报告生成后记录来源、规则命中、图谱路径、安全审查和权益扣减。
- 报告页面清楚显示免责声明和风险边界。

### 2.8 商城、会员、积分和权益

保留并强化现有商业闭环，但支付仍为人工确认。

要求：

- 商品支持报告次数包、月会员、年会员、数字资料和实物商品。
- 会员支持有效期、报告额度和会员专属能力标记。
- 积分支持获得、消耗、流水和后台调整。
- 权益支持发放、扣减、过期、补发和溯源。
- 实物商品支持 SKU 库存、收货地址、人工发货和退款申请。

### 2.9 合规和安全

报告内容必须保留风险边界。

要求：

- 保留用户协议、隐私政策、免责声明。
- 报告不得给出医疗、投资、法律等确定性高风险建议。
- 后台接口必须按角色鉴权。
- 客户只能访问自己的报告、订单、地址和权益。
- 后台敏感操作写入审计日志。

## 3. 明确不做范围

本阶段不做：

- 真实微信支付接口。
- 真实微信退款接口。
- 真实腾讯云短信接口。
- 真实快递查询接口。
- 分销代理体系。
- 专家入驻和人工咨询平台。
- 多商户商城。
- 一次性写满 518400 种命盘解释。
- 一次性完整上线六爻和奇门全部体系。
- 实时联网搜索生成报告。

这些能力可作为 1.1 或 2.0 范围继续规划。

## 4. 架构边界

### 4.1 客户端

- 微信小程序坚持原生开发，使用 WXML、WXSS、JS 和微信原生 API。
- H5 继续使用 React/Vite。
- H5 和小程序共用甄算 API 和 JSON 数据结构，但不做 H5 到小程序的代码转换。

### 4.2 后端

- Node/Express 继续作为主 API。
- PostgreSQL 存业务数据、账号、订单、权益、知识、规则、模板、报告历史和审计日志。
- Neo4j 存本体图谱、概念关系、知识关系、规则路径和报告溯源路径。
- 大模型只负责组织表达，不直接决定理论依据。

### 4.3 外部服务

- 微信真实登录要接入微信接口。
- 手机号登录继续模拟短信。
- 微信支付继续占位。
- 腾讯云短信继续占位。

## 6. 交付阶段

### 阶段 1：真实微信登录

- 小程序 `wx.login`。
- 后端微信 code 换 openid / unionid。
- 客户身份绑定和账号合并。
- 登录状态接入现有报告、商城和权益接口。

### 阶段 2：知识库发布工作流

- 知识、规则、模板草稿/发布/停用。
- 版本记录。
- 发布审计。
- 已发布内容参与报告生成。

### 阶段 3：图计算能力

- Neo4j 路径查询接口。
- 概念、知识、规则、模板、报告之间的关系建模。
- 报告生成时记录图谱命中路径。

### 阶段 4：图谱可视化后台

- 节点图、知识图、规则路径图、报告溯源图。
- 搜索、过滤、展开、详情面板。

### 阶段 5：报告分层和权益闭环

- 免费版报告。
- 付费完整版报告。
- 报告权益扣减。
- 会员和次数包策略完善。

### 阶段 6：商业和运营补强

- 商品、订单、退款、发货、积分和会员后台补强。
- 合规文案。
- 审计日志。
- 运维健康和备份检查。

## 7. 验收标准

1. 小程序可以使用真实微信登录获取客户 token。
2. 手机号验证码登录仍能使用模拟流程。
3. 支付不接真实微信接口，但人工确认支付后能完成权益发放和订单状态流转。
4. 后台可以发布知识、规则和模板，草稿不会影响线上报告。
5. Neo4j 可以查询概念、知识、规则和报告路径。
6. 后台可以可视化查看概念图、知识关系图、规则路径图和报告溯源图。
7. 免费报告和付费完整版报告可以区分生成。
8. 付费完整版报告会校验并扣减权益。
9. 报告历史中能看到规则命中、知识来源、图谱路径和安全审查。
10. 全量测试、构建、小程序静态验收通过。
